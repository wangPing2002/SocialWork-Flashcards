# 1. 项目定位

“社会工作闪卡”是一款用于社会工作考研复习的 Android 闪卡应用。

核心目标不是把大段答案简单搬进手机，而是建立：

**学习 → 主动回忆 → 熟悉/不清楚判断 → 间隔复习 → 弱卡优先 → 内容纠错 → 正式题库修订**

的完整学习闭环。

主要特点：

- Android 原生离线应用；
- 不需要账号；
- 学习数据默认只保存在本机；
- 支持每日学习量；
- 支持继续学习；
- 复习内容只来自已经学习过的卡片；
- 支持重复复习；
- 最近 10 次学习结果参与排序；
- 多次“不清楚”的卡片会更频繁出现；
- 例子、完整答案按需展开；
- 支持本地修改卡片内容；
- 支持标记内容错误并导出反馈；
- 支持完整学习数据备份与恢复。

# 3. 核心学习逻辑

## 3.1 每日学习量统一

不再区分：

- 每日复习量
- 每日新学量

统一为：

**每日学习量**

例如设置为 30 张：

- 当天尚有学习额度时，“开始学习”会生成当天剩余数量的智能队列；
- 当天目标完成后，可以继续加练；
- “继续学习”不会重新抽卡，而是从上次中断的位置继续。

## 3.2 学习与复习的边界

严格遵守：

> **复习只能从已经学习过的卡片中产生。**

未学习卡不会被系统作为“复习卡”抽取。

已学习卡可以：

- 重复复习；
- 多次进入学习队列；
- 根据薄弱程度提高出现频率。

## 3.3 固定卡片尺寸

主卡片区域保持固定尺寸，避免：

- 翻答案后页面突然变高；
- 不同卡片尺寸频繁变化；
- 长答案破坏记忆节奏。

较长内容使用：

- 卡片内部滚动；
- “例子”按钮；
- “完整答案”按钮。

# 5. 智能复习规则

每张卡保存最近 **10 次**：

- 熟悉
- 不清楚

排序综合考虑：

1. 是否已经学习；
2. 是否达到间隔复习时间；
3. 最近 10 次“不清楚”的比例；
4. 最近连续“不清楚”的次数；
5. 距离复习到期时间。

## 5.1 弱卡优先

多次“不清楚”的卡片：

- 会更早进入队列；
- 会获得更高抽取权重；
- 在一次学习任务中允许重复出现。

当前设计目标：

- 一般卡：通常 1 次；
- 中度薄弱卡：可出现约 2 次；
- 高度薄弱卡：可出现约 3 次；
- 避免同一张卡连续出现。

## 5.2 间隔复习

总体采用基于遗忘规律的间隔设计。

曾使用的基础间隔：

`10分钟 → 30分钟 → 12小时 → 1天 → 2天 → 4天 → 7天 → 15天 → 30天 → 60天`

实际优先级还会叠加最近 10 次表现，因此并非机械按固定时间排序。

# 6. 内容纠错与本地修正

从 **V2.1** 起加入内容纠错系统。

## 6.1 标记“内容有误”

学习页可以直接标记：

- 答案内容有误
- 题目表述有误
- 出处/章节有误
- 例子或扩展答案有误
- 知识点重复或冲突
- 其他

同时可以填写备注。

例如：

> “教材第十章这里应为过程目标，不是结果目标。”

## 6.2 本地修正

用户可以直接修改：

- 题目
- 答案要点
- 记忆提示
- 出处
- 例子
- 名词解释完整答案
- 简答完整答案
- 论述/案例完整答案

## 6.3 本地数据库

内容修正与反馈保存在：

`content_feedback.db`

本地修改不会直接覆盖：

- `cards.json`
- `details.json`

这样可以保留：

**原始正式题库 + 用户本地修正版**

两层数据。

## 6.4 导出反馈 JSON

可以导出：

- `reports`
- `cardOverrides`
- `detailOverrides`

将 JSON 上传给 ChatGPT 后，可以：

1. 找到具体问题卡；
2. 查看用户备注；
3. 回到教材/真题重新核验；
4. 修改正式题库；
5. 在后续版本中合并。

> ChatGPT 无法自动读取手机私有数据库。必须由用户主动导出并上传反馈文件。

固定：

```text

```

严格执行：

> **只迁移，不清空。**

允许：

- 新增表；
- 新增字段；
- 转换旧数据；
- 增加索引。

避免：

- 删除用户表；
- 重新创建整个数据库；
- 为了开发方便清空历史记录。

# 8. 内容准确性规范

从 V2.1 起，新增与修订闪卡统一遵守以下标准。

## 8.1 资料优先级

优先级从高到低：

1. 指定教材、用户上传教材原文与明确标注内容；
2. 东南大学历年真题及用户提供的真题资料；
3. 用户提供的高分答案、章节讲义与备忘录；
4. 只有用户明确要求“补充、验证、扩展”时，才使用外部资料或模型知识。

如果来源冲突：

- 不擅自揉成一个答案；
- 优先保留教材主口径；
- 必要时明确标注冲突。

## 8.2 每张正式闪卡最低要求

必须具备：

- 正式、自然的真题/教材习题式问法；
- 可核对的知识来源或章节；
- 核心答案要点能够被来源支持；
- 例子不能改变理论边界；
- 扩展理解不得伪装成教材原文；
- 无法确认的年份、题型、出处不得猜测。

## 8.3 四道检查

### A. 术语检查

核对：

- 名称
- 人物
- 年份
- 理论归属
- 阶段
- 模式
- 原则

不得随意混淆相近概念。

### B. 问题检查

题目要像：

- 真题
- 教材习题
- 正式考试问法

禁止使用内部提示式问题。

### C. 答案检查

短卡要求：

- 碎片化；
- 简短；
- 完整；
- 按重要性排序。

长答案要求：

- 总—分—总；
- 分点互不重复；
- 不为了凑内容添加来源未支持的细节。

### D. 来源检查

- 出处放答案/详情页；
- 正面题目不显示出处；
- 真题年份、科目、题型只有资料确认后才写；
- 无法确认时写“教材相关章节”或“当前资料未确认”。

## 8.4 用户反馈闭环

正式修订流程：

1. 用户在 App 中标记错误；
2. 导出反馈 JSON；
3. 上传给 ChatGPT；
4. 回到教材/真题核验；
5. 修改 `cards.json` / `details.json`；
6. 在 README 更新记录中写明修订；
7. 发布新 APK；
8. 无法确认的争议项保留“待核实”。

核心原则：

> 宁可少一张卡，也不要多一张不可靠的卡。  
> 宁可明确“资料不足”，也不要用看似完整的内容填补证据空白。

# 10. 固定 Release 签名

从 V2.2 开始，正式发布统一使用同一份 Release keystore。

只要：

- applicationId 不变；
- Release keystore 不变；
- versionCode 递增；
- 正常覆盖安装；

后续版本就可以保留已有用户数据。

## 10.1 创建 keystore

只创建一次。

Windows PowerShell：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\create-release-keystore.ps1
```

脚本会生成：

```text
socialwork-release.keystore
socialwork-release.keystore.base64.txt
```

### 极其重要

`socialwork-release.keystore` 必须永久保存。

不要：

- 上传公开 GitHub；
- 删除；
- 每个版本重新生成。

如果丢失，未来将无法用同一签名覆盖升级已经安装的正式版本。

## 10.2 GitHub Secrets

GitHub 仓库：

`Settings → Secrets and variables → Actions → New repository secret`

添加：

```text
ANDROID_KEYSTORE_BASE64
ANDROID_KEYSTORE_PASSWORD
ANDROID_KEY_ALIAS
ANDROID_KEY_PASSWORD
```

## 10.3 发布 Release APK

例如：

```powershell
git tag v2.2.0
git push origin v2.2.0
```

GitHub Actions 的 Release workflow 会生成签名 Release APK。

未来：

```text
V2.2
↓
V2.3
↓
V2.4
↓
V3.0
```

必须始终使用同一份 keystore。

## 10.4 从旧 Debug APK 迁移

旧的 GitHub Runner Debug APK 可能使用不同 debug 签名。

因此，如果：

- 手机上已有旧 debug APK；
- 新 Release APK 提示签名冲突；

Android 无法直接覆盖。

切换正式 Release 前建议：

1. 先在旧 App 中导出全部学习数据；
2. 保存备份文件；
3. 再进行正式 Release 版本迁移；
4. 安装后导入备份恢复数据。

一旦完成固定 Release 签名迁移，之后就可正常覆盖更新。

# 14. 后续版本文档规则

从现在开始，**README.md 是项目唯一的主要说明文档**。

以后例如发布：

```text
V2.3.0
V2.4.0
V3.0.0
```

不再新增：

```text
CHANGELOG_V2.3.md
CHANGELOG_V2.4.md
RELEASE_SIGNING_NEW.md
CONTENT_ACCURACY_NEW.md
NEW_CARDS_xxx.md
```

而是直接在 README 的：

```text
# 13. 版本更新记录
```

下面追加：

```markdown
## V2.3.0

### 新增功能
- ...

### 内容修订
- ...

### 数据库变更
- ...

### 题库新增
- ...

### Bug 修复
- ...
```

如果某项规范发生变化，例如：

- 签名规则
- 内容准确性标准
- 数据库结构
- 题库组织方式

则同时修改 README 对应的正式章节，并在版本更新记录中写明变化。

这样可以保证：

> **README 始终代表项目当前真实状态，版本记录则保留历史变化。**
